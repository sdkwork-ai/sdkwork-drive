# Drive Admin Storage API Changelog

## 0.2.0

- Object operations accept a bucket override, so the admin console browses the buckets that actually exist on the provider account instead of only the one bucket named in the provider configuration. `GET .../objects` (`storageProviders.objects.list`), `GET .../objects/{objectKey}` (`storageProviders.objects.retrieve`), `DELETE .../objects/{objectKey}` (`storageProviders.objects.delete`), and `GET`/`PUT .../object-contents/{objectKey}` (`storageProviders.objects.content.retrieve` / `.update`) take an optional `bucket` query parameter; `storageProviders.objects.copy` takes an optional `sourceBucket` body field next to the existing `destinationBucket`. The parameter is optional and absent means the configured bucket, so the change is additive for every existing caller. The endpoint, region, and credentials always come from the named provider configuration; only the bucket is overridden, and it is validated against the S3 bucket-name rule before use.
- New object content endpoints: `GET`/`PUT /backend/v3/api/drive/storage/providers/{providerId}/objects/{objectKey}/content` (`storageProviders.objects.content.retrieve` / `storageProviders.objects.content.update`). Reads return base64 content up to 8 MiB with size and SHA-256 checksum; writes accept utf8 or base64 payloads with an optional content type. A trailing-slash object key with empty content creates a directory placeholder object.
- Object content endpoints moved from `.../objects/{objectKey}/content` to `.../object-contents/{objectKey}`: the previous path collided with the `{*objectKey}` tail wildcard of the object head/delete route and panicked at router construction in production assembly (axum 0.8 wildcard overlap). The new path keeps the wildcard at the end of the route.
- Object keys in path parameters are decoded exactly once by the framework; the previous manual second percent-decode silently rewrote literal `%` characters (e.g. `50%20off.txt` became `50 off.txt`) and rejected keys with trailing percent sequences. Trailing-slash keys are normalized to a single slash, double-slash keys are rejected, and directory placeholder objects are now deletable through `DELETE .../objects/{key}/` like any other object.
- `storageProviders.buckets.list` rows carry the vendor-reported `region` (`ProviderBucketListItem.region`, additive and omitted only when the vendor reports none through either channel described below). The inventory is an account-level read that spans regions, so the region is a property of the row — it is what the console shows as the bucket's region and what a later object operation needs in order to address that bucket's own endpoint.
- `storageProviders.buckets.list` rows carry the vendor's own region for every vendor that publishes one, resolved through three channels in order. AWS-style inventories send `<BucketRegion>`, which the SDK's generated `Bucket` shape parses; Tencent COS, Alibaba Cloud OSS and their peers send `<Location>` instead, an element that shape has no member for, so the inventory client's HTTP layer keeps a copy of the inventory body and reads it there (the SDK's own default connector is wrapped, not replaced: same hyper 1.x + rustls 0.23 stack, and only the inventory client buffers a response). A bucket neither channel names gets one bounded, individually timed `GetBucketLocation` call, which resolves it only when it lives in the configured endpoint's own region — a cross-region ask is answered `404 NoSuchBucket`, with no redirect and no region hint (probed against `cos.ap-guangzhou.myqcloud.com` for an `ap-beijing` bucket), the account-level service host refuses bucket operations (`400 InvalidArgument`), and the global acceleration host requires per-bucket acceleration (`BucketAccelerateNotEnabled`). A bucket the vendor answers for on none of the three keeps `ProviderBucketListItem.region` omitted rather than being guessed from the configured endpoint. Buckets already answered are never looked up again, and the lookups are bounded per inventory read and best effort.
- Object operations take an optional `region`: the `region` query parameter on `storageProviders.objects.list` / `.retrieve` / `.delete` / `.content.retrieve` / `.content.update`, and the `region` body field on `storageProviders.objects.copy`. It names the region the addressed bucket lives in, exactly as the bucket inventory reports it for that row; the server then addresses that bucket's own regional endpoint following the vendor's own endpoint convention (the region is part of the endpoint host for the vendors that publish it there). Absent — or a vendor convention that cannot express another region, such as a proxy, a private gateway, or a single-endpoint vendor — keeps the endpoint the provider configuration stores, so every existing caller is unaffected. The value is validated as a vendor region code before it is allowed anywhere near the endpoint host, and an invalid one is rejected with `40003` before any vendor call.
- `storageProviders.buckets.list` reads a Tencent COS account's bucket inventory through the vendor's account-level service host (`service.cos.myqcloud.com`) instead of the regional object endpoint the provider configuration stores. COS answers the account inventory (`GetService`) for the region named in the endpoint, so a COS account holding buckets in several regions listed only the one bucket that sits in the configured region. Every other vendor keeps listing through its configured endpoint, an endpoint that is not the vendor's own domain (a proxy, a private gateway, a test double) keeps answering the inventory itself, and the service host falls back to the configured endpoint when it cannot answer.
- The storage provider/bucket management surface becomes the canonical owner for the CloudRouter storage center: CloudRouter no longer serves `/backend/v3/api/storage/providers|buckets`, and its admin UI browses bucket objects through this API (see CloudRouter backend API changelog 0.12.0).

## 0.1.0 — 2026-06-24
